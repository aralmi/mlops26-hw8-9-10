# Четыре дефекта учёта экспериментов

## 1. Несколько конфигураций записывались в один run

В исходном `src/sweep.py` дочерний `start_run` стоял снаружи цикла по
конфигурациям. Все шесть обучений попадали в один `all-candidates`.
`run_candidate` записывал параметры только в пустой run: следующие модели
получали уже чужие параметры, а метрики и артефакты смешивались.
Имя в локальном списке не делало эти результаты отдельными экспериментами.

Исправление: каждый проход цикла открывает собственный nested run с именем
конфигурации, общий sweep остаётся родителем. Все шесть меняют lr, r и
target_modules; seed, вход, val и бюджет одинаковы. Конфиги, исходники,
uv.lock, параметры, train/val curves и настоящий модельный пакет сохраняются
в каждом run. `docs/comparison.csv` строится из MLflow API, а не из вручную
перенесённых чисел.

Доказательство: проверка 1 требует шесть отдельных FINISHED runs, проверка 3
сопоставляет их реальные параметры и число train/val-точек с конфигом.
ID, URL, параметры, метрики и кривые вынесены в `docs/results/run-manifest.json`.

## 2. Артефакты терялись при замене контейнера

У PostgreSQL уже был volume, но путь `/mlartifacts` оставался во временной
файловой системе контейнера MLflow. Записи runs переживали пересоздание,
а соответствующие им файлы могли исчезнуть. Живой сервер сразу после
обучения не доказывал сохранность данных.

Исправление: `artifacts:/mlartifacts` подключён к сервису MLflow.
Метаданные и файлы находятся в двух именованных volumes. `make down`
не удаляет volumes; команду `down -v` для этого проекта выполнять нельзя,
если нужны накопленные результаты.

`make check-storage` создаёт отдельный run с probe-файлом, сохраняет его
SHA256, выполняет настоящий `--force-recreate` только сервиса MLflow,
скачивает файл через API и сверяет хеш. Проверка 8 повторно скачивает
probe и сверяет версию compose. Фактический результат —
`docs/results/storage-check.json`. Загрузка candidate в новом процессе
в проверке 7 дополнительно показывает, что сохранённый пакет работоспособен.

## 3. У runs отсутствовали версии train и val

`provenance()` уже вычислял хеши, но `main()` в sweep явно выбрасывал
все ключи `data_*`. Параметры модели и Git SHA не показывают, какие тензоры
действительно использовались. Данные могли поменяться без изменения кода.

Исправление: весь provenance передаётся родителю и каждому кандидату.
Логируются SHA256 train/val, код всех файлов src, нормализованный конфиг,
Git SHA и признак dirty. База закреплена точной 40-символьной ревизией HF;
manifest адаптера содержит ту же ревизию. Данные и разметка дополнительно
версионируются DVC.

В `docs/data-lineage.json` сохранены исходный репозиторий ДЗ4, коммит,
SHA256 тензоров/сырого train и связь всех 1388 id. Отдельная повторная
токенизация кодом ДЗ4 проверила input_ids, attention_mask и labels.
Это сильнее, чем сравнение сырых вопросов с двоичными файлами по строкам.
Проверка 2 и `select()` отвергают отсутствующие или устаревшие хеши.

## 4. Порог вычислялся, но не ограничивал регистрацию

Исходный `promote()` считал final/base, но сразу вызывал регистрацию
и менял alias. Даже отрицательный результат проверки качества не останавливал
изменение реестра. Пометка `validation=passed` могла быть записана без gate.

Исправление: первым вызывается `gate(run, threshold)`. Он требует FINISHED,
конечные числа, положительный base loss и допустимое отношение. Только
после его успеха создаётся версия и меняется alias candidate.
Проверка 6 пробует нулевой порог: положительный loss обязан дать отказ.
Дополнительный тест также проверяет, что при отказе ни регистрация,
ни изменение alias вообще не вызываются.

Этот loss-порог не равен разрешению на выпуск. Для champion используется
`evaluation.solution.quality_gate` и команда `make promote`, которая заново
сверяет протокол, модели, raw-хеши и пересчитанные метрики. Плохие ответы
не выкидываются из знаменателя. Общие accuracy/format_rate и критические
срезы не могут ухудшиться; все обязательные behavioral должны пройти.

Отрицательная проверка портит отдельную копию raw-ответов. Counts и
per_item пересчитываются согласованно: отказ должен быть связан с реальным
нарушением условий качества, а не только с подделанной цифрой в отчёте.
Исходные ответы, веса, baseline и aliases эта проверка не меняет.

## Ограничения компьютера и дополнительные проверки

Используется CPU float32 и тот же стек PyTorch/Transformers/PEFT, который
работал в ДЗ5. MPS в предыдущей работе давал нечисловые градиенты; повторять
этот риск для обязательного короткого поиска не потребовалось. Бюджет
задания не увеличен: четыре шага, train-пул 32, val 8, accumulation 2.

Ответы в собственном ДЗ4 доходят до 3456 токенов. Полный logits-тензор
по всему словарю расходует лишнюю память. Из ДЗ5 перенесён блочный causal
loss по позициям ответа и gradient checkpointing на длинных входах.
Нормировка накопления остаётся по общему числу целевых токенов группы.
Неконечный градиент останавливает обучение до optimizer.step.
Дополнительный unit-тест сравнивает loss и все обучаемые градиенты с
полным causal loss на небольшом примере.

Исходные файлы `tests/` не изменены, отпечаток **c42ac7788026**.
24 исходных unit/integration-теста работают на синтетических фикстурах:
они проверяют логику, а не заменяют реальные ответы Qwen.
Восемь дополнительных тестов находятся отдельно в `verification/`.
Фактические ответы, решение gate и окончательные результаты приёмки
приведены в `docs/conclusion.md`, `docs/results/` и `docs/check-all.txt`.
